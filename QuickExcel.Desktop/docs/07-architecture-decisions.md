# QuickExcel 架构决策记录

日期：2026-10-22。本记录解释目标方案的依据、代价及重新评估条件。**已选方向**表示后续实现应遵循的设计，并不代表相关功能已经落地；**待验证**必须在指定里程碑以实验或兼容性证据收敛。当前事实与实施状态以 [文档首页](README.md) 为准。

## ADR-001：Windows 优先，WPF 作为首个桌面界面

**状态：已选方向；当前原型已采用。**

沿用 C#/.NET 与现有 WPF 原型，优先打通本地文件、键盘编辑、撤销和脚本工作流。领域与应用层不依赖 WPF，后续跨平台可以替换呈现层，不因未来可能跨平台而现在重写所有基础能力。

代价是首个 Beta 仅支持 Windows x64。跨平台不是本阶段的验收条件。若目标用户或分发渠道明确需要 macOS/Linux，再独立评估 Avalonia 等界面方案；不能把仅编译领域层视作已经支持另一个操作系统。

## ADR-002：ExcelIO 保持独立，编辑器使用带类型的领域模型

**状态：已选方向；M1/M2 实施。**

现有 `XlCell.Value` 以字符串为主，不足以区分文本、数值、布尔、错误和空白。新文档模型使用显式 `CellValue`，将输入内容、公式计算结果和显示文本分开。日期以 Excel 数值序列、日期系统和格式组合表达，不自动给全部数值附加 DateTime 身份。

ExcelIO 继续承担文件读写；需要增强类型读写时，以兼容既有公共 API 的最小扩展或专门适配完成。新编辑器不直接依赖全局静态变更回调。代价是过渡期需要模型转换和夹具，不能凭适配器恢复历史文件已经丢失的类型。

完成条件是类型与日期语义往返、稀疏存储和旧库回归均通过。若 double 无法满足将来的精确财务场景，另行设计显式 Decimal/BigInt 能力与格式版本，不能静默改变现有 Number 语义。

## ADR-003：模块先分边界，再按需要拆程序集

**状态：已选方向；M1 开始。**

采用 Domain、Core、Calculation、Storage、Scripting、ScriptContracts、Desktop 的职责划分。Core 定义端口，具体适配器在启动组合根注入；Worker 只依赖协议和原生适配子模块，不反向引用桌面客户端。

首先用命名空间、接口和依赖检查建立边界，出现独立发布或编译约束时再拆项目。代价是需要持续检查内部依赖，不能仅以目录名代表隔离。未来模块需要独立复用、测试或分发时，依据实际引用图拆分，不默认每个服务一个程序集。

## ADR-004：文档会话单写入队列，修改通过事务命令

**状态：已选方向；M1 实施。**

每个打开实例有独立 `DocumentSession`。用户输入、粘贴、结构编辑、撤销及脚本动作都先预检，再原子提交 `ChangeSet`。短写操作串行；昂贵计算和 I/O 使用快照并在后台执行。

这让撤销、保存与脚本动作共享一致语义。代价是复制/持久化快照和历史占用内存，需要结构共享或局部快照以及明确预算。不能为减少内存而让后台任务读取正在修改的可变对象。未来若确需协同编辑，应另立操作合并协议；当前单写入规则不能直接假装成为分布式一致性方案。

## ADR-005：统一计算调度器，用修订和代次防止旧结果覆盖

**状态：已选方向；M1 建立门禁，M3 完成计算迁移。**

工作簿级调度器维护跨表依赖，使用类型化求值和增量失效。每个结果关联会话、输入修订、计算代次和脚本代次。取消仅节省资源，结果有效性由提交时核验保证；撤销同样提升修订，不恢复历史修订号。

代价是要维护依赖图、错误状态和可重现调度测试。先做完整重算作为正确性参考，再与增量路径逐次比较。旧 `FormulaEngine` 和新调度器不能同时监听并提交同一文档。动态数组、异步 UDF 和迭代循环计算需要单独设计，不以未定义行为塞进此调度器。

## ADR-006：XLSQ 使用 ZIP 容器，内嵌 XLSX 为内容唯一来源

**状态：已选方向；v1 已存在，v2 在 M2 实施。**

扩展名固定为 `.xlsq`。保留 `workbook.xlsx` 作为单元格、公式、样式、名称和工作表顺序的唯一持久化来源；manifest 与状态文件保存版本、稳定身份、脚本绑定和缓存有效性。脚本存 UTF-8 源码，不保存引擎字节码或有效执行授权。

代价是 XLSX 本身与外层 ZIP 有嵌套开销，且需共同预算。优点是不会出现 JSON 与 XLSX 各有一份单元格内容而无法判断谁是最新的情况。确需超大表随机访问时，再以测量决定新容器版本或可选数据部件，不在 v2 中暗中引入第二份事实来源。具体字段仅以 [格式专题](03-file-format-and-compatibility.md) 为准。

## ADR-007：兼容性按能力声明，导出有快照和可移植公式两种语义

**状态：已选方向；当前仅快照导出，M2/M3 扩展。**

XLSX 是交换格式，不等同于完整 Excel 行为。当前导出公式缓存为值。目标增加保留受支持标准公式的模式，但 JS 函数及其跨表传递依赖必须按导出计划冻结为值；旧缓存需等待重算或由用户明确选择。

未知部件只在可判断未失效时原样保存；存在损失必须说明受影响对象并允许取消或另存。代价是部分复杂 Excel 文件不能无提示编辑保存。若真实用户的常用文件要求更高兼容性，应扩充已验证支持矩阵，而不是通过“兼容 xlsx”措辞跳过测试。

## ADR-008：保留真正 QuickJS，引擎版本固定并追踪来源

**状态：已选方向；当前使用 QuickJS-NG 0.17.0。**

沿用现有 QuickJS-NG native bridge，独立记录源码版本、哈希、构建参数、补丁和许可证。通过运行时门面隔离 P/Invoke，不以另一种 JS 引擎冒充 QuickJS。当前来源见 [native/SOURCES.md](../../QuickExcel.Scripting/native/SOURCES.md)。

代价是 Windows 原生构建、ABI、资源管理和引擎漏洞升级需要持续维护。升级先跑语言/桥接/限制/崩溃/性能回归；引擎字节码不进入 `.xlsq`，避免保存格式与某个引擎二进制版本强绑定。若引擎维护或 ABI 成本不可接受，重新评估实现，但必须明确语言差异与文件迁移要求。

## ADR-009：默认每文档 worker，进程隔离与 OS 访问控制分别验证

**状态：worker 方向已选；OS 机制待 M4 验证、M6 放行。**

独立 worker 允许超时终止和原生崩溃隔离。宿主控制协议、预算、源码授权与结果提交；不接受 worker 请求任意系统操作。每文档运行时串行执行，避免 QuickJS 对象跨线程并发访问。

Job Object 用于进程管理和资源限制，文件/网络访问仍需要独立安全机制。其职责边界依据 [Microsoft Job Objects 文档](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)。M4 比较受限令牌与 AppContainer 等策略对 native DLL、运行库、管道和便携分发的影响，最终依据实际发布包的系统调用测试作决策。

代价是进程内存、启动时间与 IPC。可通过按需启动、批量调用和关闭释放控制，但不提前采用共享 worker 池牺牲文档隔离。若 OS 策略未通过门禁，只能发布明确限定可信脚本的试用候选，不算完成 M6 Beta，也不能宣称任意第三方脚本安全。该限制不阻挡用户关闭脚本使用表格本身。

## ADR-010：UDF 显式输入；动作脚本只提出变更

**状态：已选方向；v1 UDF 已有，完整契约 M3/M4 实施。**

UDF 接收显式参数，返回受支持的标量或错误，不直接读写活动工作簿。现有 v1 区域仍是一维参数；二维区域、描述符和命名空间需显式 API 版本选择。不得静默改变已保存脚本的参数形状。

动作脚本由用户运行，在只读快照上产生有界 patch；宿主检查 baseRevision、权限和容量后一次提交。撤销重放已记录的数据，不重跑脚本。代价是作者需要理解函数和动作两类入口，以及冲突时重新运行。

可变闭包和时间/随机输入会破坏 UDF 纯度；禁用部分全局对象不足以证明确定性。M3 先冻结执行契约：含 JS 的工作簿采用每轮重建上下文、稳定顺序完整重算，不复用 UDF 及下游的未变结果。M4 落实 worker 严格策略，经过验证后才能优化 JS 增量路径；确定性等价承诺始终限定已验证子集。网络、异步任务、外部凭据及任意 OS API 均需后续单独设计，不属于首个 Beta。

## ADR-011：保留 DataGrid 直到性能 spike 证明替换必要

**状态：待验证；M5 UI-002 决定。**

当前 WPF DataGrid 可快速验证交互。先建立 `IGridSurface` 隔离选区、编辑、可见区域与绘制，使用固定大表负载测量，再决定继续适配、局部绘制或替换控件。WPF 的 UI 虚拟化与数据虚拟化是两件事，启用控件虚拟化并不能自动避免大量数据对象分配。依据 [Microsoft WPF 控件性能文档](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/optimizing-performance-controls)。

保留控件降低原型迁移成本；自绘可提升可控性，但增加 IME、无障碍、编辑焦点和高 DPI 工作量。决定依据是 [质量专题](06-quality-performance-and-delivery.md) 的滚动、延迟、内存和可访问测试，不以外观偏好替代验证。更换控件不改变领域与命令契约。

## ADR-012：原子显式保存与恢复草稿分开

**状态：已选方向；基础原子保存已有，M2 接入、M6 完善。**

显式保存从一致快照生成候选文件，在同目录完成写入与校验后替换目标；只有保存的修订被标记为已保存。自动恢复写独立草稿，不能把“用户尚未选择保存”变成静默覆盖原文件。检测外部修改后要求选择处理方式。

恢复记录、文件历史和诊断均可能包含用户数据，默认留在本地并有清理规则；恢复不带入脚本执行授权。代价是需要草稿索引、清理、冲突和故障注入测试。网络盘、同步盘等文件系统的原子性不未经验证就承诺；平台行为边界写入支持矩阵。

## ADR-013：发布模式由干净环境试验决定，保留可追溯构建

**状态：当前 framework-dependent；Beta 分发模式待 M6 决定。**

当前 Windows x64 包依赖 .NET 10 Windows Desktop Runtime。Beta 比较 framework-dependent 的体积与运行时前置条件，以及 self-contained 的体积与运行时更新责任。两者都必须提供完整目录、native DLL、许可证及版本信息，不能只交付单个 EXE 并假设其可运行。

默认不把安装器、自动更新服务或文件关联作为核心正确性的前置要求。若提供安装器，检查卸载不会删除用户文档；若提供更新，先单独定义校验、回退和运行时升级机制。发布候选必须在无 SDK 的干净 Windows 环境实测，编译成功不代替安装验收。

## 决策维护

每项变更追加新的结论与依据，保留旧取舍的简短记录。先变更契约再变更实现，涉及文件或脚本 API 的不兼容变更必须关联版本策略和迁移测试。尚未验证的选择保留状态、负责人角色和截止里程碑，不能在发布文案中变成已经交付的保证。
